    Ce document est un produit de l'IA Claude d'Anthropic. Il fait suite au document Introduction étape par étape au framework web [Spring MVC] (2026), qui faisait lui-même suite aux documents Introduction étape par étape au framework web [ASP.NET Core MVC] et Introduction étape par étape au framework web [NestJS] (2026). Le présent document transpose le cours [Spring MVC] dans le monde [Python] :

    • le framework [Spring MVC] et le langage [Java] sont remplacés par le framework [Flask] 3.1 et le langage [Python] (version 3.12 ou plus récente) ;
    • les vues [Thymeleaf] sont remplacées par des vues [Jinja2], le moteur de vues de [Flask] ;
    • la validation [Bean Validation] est remplacée par la bibliothèque [Pydantic] (les paramètres des actions) et par la bibliothèque [WTForms] (les formulaires HTML) ;
    • [Spring Security] est remplacé par quelques dizaines de lignes de [Python] écrites pour l'occasion, qui s'appuient sur les bibliothèques [PyJWT] (les jetons JWT) et [bcrypt] (le hachage des mots de passe) ;
    • l'ORM [Hibernate] et [Spring Data JPA] sont remplacés par l'ORM [SQLAlchemy], toujours avec une base [MySQL].

    Le document suit exactement la progression du cours [Spring MVC] : d'abord de nombreux petits projets, chacun centré sur une notion, puis une étude de cas complète, une application web de prise de rendez-vous pour un cabinet de médecins, dont tous les fichiers sont commentés. Les exemples portent les mêmes numéros et traitent les mêmes sujets que dans les cours [Spring MVC] et [ASP.NET Core MVC] : un lecteur qui connaît l'un de ces cours peut comparer les frameworks exemple par exemple. Ce n'est pourtant pas nécessaire : ce document se lit seul, et ne suppose aucune connaissance de [Spring] ni d'[ASP.NET]. On suppose seulement connues les bases de la programmation web (le protocole HTTP, le langage HTML) et celles du langage [Python] (fonctions, classes, dictionnaires, modules). Un précédent cours du réviseur de celui-ci, Introduction au langage Python et au framework web Flask par l'exemple (2020), présente le langage [Python] lui-même, pour qui aurait besoin de le découvrir d'abord.

    1.1. La place de Flask dans une application web

    Une application web est souvent construite en couches, chaque couche ne parlant qu'à ses voisines :

    • la couche web reçoit les requêtes HTTP du navigateur et lui renvoie des pages HTML. C'est elle que [Flask] nous aide à écrire ;
    • la couche métier contient les règles de gestion de l'application (« un patient ne peut avoir qu'un rendez-vous à venir », par exemple). Elle ignore tout du web : elle pourrait aussi bien servir une application en ligne de commande ;
    • la couche d'accès aux données (couche [DAO], pour [Data Access Object]) lit et écrit dans la base de données. Nous utiliserons [SQLAlchemy], un ORM ([Object Relational Mapper]) qui fait correspondre les lignes des tables et des objets [Python].

    La couche web suit elle-même le modèle [MVC] ([Model – View – Controller]) :

    • le contrôleur (C) est un ensemble de fonctions [Python], appelées actions, qui traitent chacune un type de requête (par exemple [GET /agenda]). Une action lit les paramètres de la requête, fait travailler la couche métier, puis choisit la vue à afficher ;
    • le modèle (M) est l'ensemble des données que l'action transmet à la vue ;
    • la vue (V) est un fichier [Jinja2] (extension [.html]) : une page HTML qui contient des expressions [{{ ... }}] et des instructions [{% ... %}] ([{% if %}], [{% for %}]...), que le moteur [Jinja2] remplace par les données du modèle.

    Une remarque de vocabulaire, pour éviter une confusion : la documentation de [Flask] appelle view function (« fonction de vue ») la fonction qui traite une requête, et template (« gabarit ») le fichier [Jinja2]. Ce document garde le vocabulaire du modèle [MVC], celui des cours [Spring MVC] et [ASP.NET Core MVC] : la fonction qui traite une requête est une action, le fichier [Jinja2] qui fabrique la page est une vue, et le mot gabarit désigne la vue commune dont les autres pages héritent (chapitre 4).

    Le traitement d'une requête suit les étapes numérotées du schéma :

    • 1 : le navigateur envoie une requête HTTP, par exemple [GET /agenda?idMedecin=1&jour=2026-09-26] ;
    • 2 : le serveur web reçoit la requête et la confie à l'application [Flask]. Pendant le développement, ce serveur est celui de [Werkzeug], la bibliothèque sur laquelle [Flask] est bâti ; en production, ce sera un serveur comme [Waitress] ou [Gunicorn]. [Werkzeug] compare le chemin demandé aux routes de l'application et choisit l'action chargée de cette requête : c'est le routage. Avant l'action, la requête peut encore traverser des fonctions exécutées pour toutes les requêtes ([before_request]), que nous découvrirons au fil des chapitres ;
    • 3 : l'action demande à la couche métier les données dont elle a besoin ; la couche métier s'adresse, si nécessaire, à la couche [DAO], qui interroge la base [MySQL] en SQL ;
    • 4 : l'action construit le modèle M de la vue et demande au moteur [Jinja2] de fabriquer la page (fonction [render_template]) ;
    • 5 : la page HTML fabriquée par la vue est la réponse de l'action, que [Flask] renvoie au navigateur.

    [Flask] est l'un des deux frameworks web les plus utilisés du monde [Python], avec [Django]. Gratuit et libre, il fonctionne partout où fonctionne [Python] ([Windows], [Linux], [macOS]). C'est un micro-framework : son cœur est volontairement petit (le routage, les requêtes et les réponses, les sessions, les vues [Jinja2]), et tout le reste (la validation des formulaires, l'accès aux bases de données, l'authentification...) est confié à des bibliothèques choisies par le développeur. Là où [Spring Boot] configure lui-même un ensemble cohérent de composants, [Flask] laisse le développeur assembler les siens : l'application est plus explicite, et l'on voit tout ce qui s'y passe. C'est d'ailleurs ce qui en fait un bon outil pour apprendre : presque rien n'est caché. [Flask] sait fabriquer aussi bien des serveurs qui renvoient du JSON à un client [JavaScript] ([Angular], [React], [Flutter]...) que des applications web classiques, où c'est le serveur qui fabrique les pages HTML, le navigateur se contentant de les afficher. C'est ce second usage qu'étudie ce document. Deux idées de [Python] reviennent à chaque page : les décorateurs ([@app.get("/")], [@app.before_request]...), qui associent une fonction à un rôle, et le passage explicite des objets dont chaque fonction a besoin, là où [Spring] les injecte automatiquement.

    1.2. Les outils utilisés

    Les exemples ont été écrits et testés avec les outils suivants (leur installation est décrite en annexe) :

    • [Python] 3.13 (toute version 3.12 ou plus récente convient). L'installeur de [Python] fournit aussi l'outil [pip], qui télécharge et installe les bibliothèques, et le module [venv], qui crée des environnements virtuels (nous verrons plus bas ce que c'est) ;
    • l'éditeur [Visual Studio Code], avec l'extension [Python] de Microsoft (elle installe aussi l'extension [Pylance], qui analyse le code) ;
    • un navigateur récent ([Chrome], [Firefox], [Edge]) ;
    • l'outil en ligne de commande [curl], qui affiche les réponses HTTP brutes (il est livré avec [Windows] 10 et 11) ;
    • le SGBD [MySQL] (ou [MariaDB]), par exemple celui de [Laragon] sous [Windows], à partir du chapitre sur l'accès aux données, et pour l'étude de cas.

    Contrairement au [JDK], qui ne contient pas [Spring], [Python] est livré avec une bibliothèque standard très riche ; mais [Flask] et les autres bibliothèques du document n'en font pas partie : [pip] les télécharge depuis le dépôt [PyPI] ([Python Package Index]) lors de l'installation (il faut donc être connecté à Internet ce jour-là).     Note du réviseur : je conseille au lecteur d'exécuter immédiatement l'étude de cas comme il est indiqué dans ce qui suit. from flask import Blueprint, Flask, request

from controllers.pages import pages

# Bootstrap, partagé par les exemples : le dossier exemples/commun/bootstrap,
# désigné à partir de l'emplacement de CE fichier (et non du dossier courant)
BOOTSTRAP = Path(__file__).resolve().parent.parent / "commun" / "bootstrap"


def create_app():
    app = Flask(__name__)
    app.jinja_env.trim_blocks = True
    app.jinja_env.lstrip_blocks = True
    # un blueprint sans route, qui ne sert que des fichiers statiques : le
    # dossier BOOTSTRAP, sous l'URL /bootstrap/...
    app.register_blueprint(Blueprint("bootstrap", __name__, static_folder=BOOTSTRAP,
                                     static_url_path="/bootstrap"))
    app.register_blueprint(pages)
    • ligne 11 : le chemin du dossier [commun/bootstrap]. [__file__] est le chemin du fichier en cours d'exécution ([app.py]) ; [Path(...).resolve()] en fait un chemin absolu ; [.parent] désigne le dossier qui le contient ([15-gabarit]), et [.parent.parent] le dossier au-dessus ([exemples]). L'opérateur [/] d'un objet [Path] ajoute un élément au chemin, avec le bon séparateur ([\] sous [Windows], [/] ailleurs). Le chemin ne dépend donc pas du dossier courant : l'exemple trouve [Bootstrap] d'où qu'on le lance ;
    • lignes 20-21 : un blueprint est un groupe de routes, enregistré dans l'application (cf. exemple 02). Celui-ci n'a pas de route : il ne sert qu'à publier le dossier [commun/bootstrap] (paramètre [static_folder]) sous l'URL [/bootstrap] (paramètre [static_url_path]). Une page peut ainsi utiliser la feuille de style [/bootstrap/css/bootstrap.min.css].

    Les autres lignes de ce fichier seront expliquées avec l'exemple 15.
